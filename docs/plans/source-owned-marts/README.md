# Source-owned warehouse publication

Planning snapshot: 2026-09-29. Implemented and verified 2026-09-30; see each phase's handoff record.

## Outcome

An explicitly invoked reader can discover and query all published Google and Apple content from PostgreSQL. Each source owns the SQL and descriptions that explain its records. Publishing one source cannot replace another source’s views or metadata. Collection, refresh and publication belong to the service; the reader never runs them.

## Selected architecture

User selected on 2026-09-29: one warehouse database, private raw schema per source, one shared `marts` reader schema with source-prefixed names and source-owned publication. This matches the earlier proposal found in history. This session authorizes planning files only; implementation belongs to a subsequent requested session. Alternatives below record the decision, not an open question.

- Shared `marts`, source-owned views: retain catalog, grants and shared sync history. Each source defines and publishes only its named relations. Selected.
- Separate reader schemas were considered and not selected. They would require schema provisioning, grants, qualified catalog names and changed consumer discovery. Do not reopen this choice during implementation.

Sources remain platform-independent of destinations: keep SQL publication modules beside source implementations in their owning executable apps, not inside native clients or the generic `Source` contract. Reuse `publishPostgresViews`; no registry framework, app barrel, new connector runner, generic document model, or new dependency.

The current Apple exporter stores only `attachmentRef` for exported files, plus native text fields already present in source records (`7514de0`). Preserve that boundary: no attachment parser wiring, binary database columns, or new extracted file text. `attachmentRef` is a destination-managed absolute local path, scoped to its file field and content-addressed. It is not the original source filename, a portable URL or parsed content. NULL means this row exported no bytes; it does not distinguish locked, undownloaded or fileless records without the source fields.

Google-specific freshness becomes an ordinary source-owned view over explicitly named relations. It requires no refresh job or stored snapshot. Apple does not inherit settled reporting dates. Existing sync history already gives last successful pass and declared coverage; add observed-row summaries only where their meanings are useful and documented. A future calendar event date is not proof of freshness.

## Implementation decisions — 2026-09-30

The user approved these reversals of the text below before implementation:

- Apple views are created by the loader, not by an app publication step. `PostgresTable.withReaderView(schema, name)` (elt-postgresql) creates `marts.<source>_<snake stream>` in the same transaction as its raw table, projecting exactly its columns plus `loaded_at`, with the table's comments. Recorded reason for the elt change: the app boundary cannot make table and view creation atomic; it can only poll `to_regclass` and retry.
- Consequences: no Apple readiness polling, retry, publication-error map or shutdown aggregation (`apps/apple/src/main.ts` is unchanged). A stream whose prepare fails leaves its siblings published. A missing description fails the connection's declaration at startup; a foreign or stale view fails that stream's copy and shows in `stream_status`. View SQL is never replaced inside a load; a changed projection needs a warehouse reset.
- Apple column names stay native (quoted camelCase); view names are snake case. Descriptions: stream grain/keys/joins by hand, field provenance generated by each source's schema builder, proven meanings by hand.
- Stored references describe themselves: `FileStorage.reference` (LocalFiles: absolute local path of a content-addressed copy) becomes the `attachmentRef` comment.
- Scratch Postgres helpers live once in `elt-postgresql/testing`.
- The live warehouse is reset (`nx run infra:reset`) rather than cleaned by hand.

## Publication boundary

Use the existing app-owned `Pipeline.watch()` pass result to associate publication with a connection. Publish a source’s documented views after required raw relations exist. Successful empty streams must publish readable empty views. A failed first load can leave a required raw relation absent; do not invent an empty table or treat unavailable content as zero records.

Prefer explicit dependencies on the source’s copy targets, checked with PostgreSQL `to_regclass`, over catching arbitrary SQL errors. Missing dependencies postpone publication and retry after later passes; report the exact missing targets. A source-wide Postgres load prepares targets in one transaction: a sibling commit can make even a failed stream’s empty table durable. Readiness means SQL dependencies exist, not that the stream succeeded. No new generalized lifecycle protocol is authorized by this plan.

Publication errors use service error handling, separate from extraction history. Google’s finite run rejects with the publication cause and closes its client. Apple retains the latest unresolved publication error per source, sets failure exit status, continues other connections, and retries on the next pass of that source. Successful publication removes that source’s pending error; normal shutdown rejects with any unresolved publication errors and preserves watcher errors too. Missing required targets count as an unresolved publication gap. Do not add a timer, console output, logger or a new publication-history table. Every path must dispose clients.

For the reader, `catalog` establishes which views are available; `sync_status` and `extraction_coverage` describe extraction only, including failures and partial commits. They do not report publication failure causes or prove the installed definitions match the latest attempted publication. This plan does not promise reader-visible publication diagnostics. A failed replacement rolls back; existing readable views remain, while committed raw changes can still be reflected through them.

Once installed, ordinary views track inserts, updates and deletes without being recreated each pass. Reinstall definitions on each service startup once dependencies exist. No remembered cross-version bindings or migration path: output is disposable.

Initially publish each complete source bundle when all its raw dependencies exist; relation existence never proves a successful extraction. Reader metadata must expose failures or partial outcomes even when views can be queried. Initial source bundle readiness is the minimum design. Full acceptance requires every stream eventually readable; partial first-pass content is explicitly unavailable until that bundle is ready. Whole-source readiness is the selected minimum policy. Do not add dependency-based per-stream bundles unless a later explicit requirement changes that policy; do not silently drop streams.

## Completion criteria

All current source streams have discoverable documented reader views or a specifically approved exclusion. Raw schemas remain private. Google and all six Apple sources publish independently once their app setup succeeds. Apple currently requires Calendar Google OAuth before constructing the whole pipeline; this plan preserves that startup prerequisite, not authentication independence between sources. Re-publication, partial first loads, empty stores, deletes, watch cancellation, and cross-source ownership are verified. Descriptions explain grain, keys, joins, dates, nulls and limitations. Query-warehouse remains small and discovers the contract at runtime. No global Google freshness mutation remains.
