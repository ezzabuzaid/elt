# Each commit asks for a refresh

A derived dataset was refreshed only after a pass: after the passes of a run, and after each pass of a watch. A pass can be long. On 2026-10-31, the startup-credits app of Context Compiler crawled two lists and searched one step inside about 150 linked websites. After 15 minutes the source had committed 364 pages at its checkpoints, but `page_kinds` and `program_offers` had no rows, and no alert came: the first pass was longer than 15 minutes (#3487).

The refresh after a pass was not a rule of the data. It was where the host refreshed before ADR 0001 (commit fb4eacd8). Two rules of the destinations make a refresh safe while a copy loads:

- A refresh reads only what committed. The SQLite writer keeps the rows of a stage in connection-private TEMP tables, and no transaction stays open between commits (`sqlite-writer.ts`). A reload loads into a hidden target until it completes (ADR 0007).
- A refresh and a commit do not lock each other out. Each commit is a short transaction, and each refresh waits for one with a busy timeout. A watch already refreshed in the background while the next pass loaded (ADR 0003).

Thus the pipeline asks for a refresh each time that a copy makes rows visible in its target: at the end of each commit, once its stored files are reconciled, and when a reload replaces its target. The pipeline owns when, because only it sees the commits. Each kind of derived dataset still owns how. The requests go to `DerivedRefreshes`: one refresh runs at a time, and requests while it runs give one more refresh after it. A refresh that a later one supersedes is coalesced in this way. A run, after its passes, waits for the refresh that runs, and then refreshes each derived dataset once more. A background refresh that fails starts no more background refreshes and stops no pass. A run rejects with that failure once its passes ended, as a failed micro-batch fails a Spark query; else the last refresh's failure rejects it, as before (ADR 0002). In a watch, the failure stops the watch (ADR 0003). A stop that comes while a background refresh reads ends that refresh and is no failure: a run that its signal stops after its passes resolves as its passes did, as before. The refresh code is now in one place, so the copy in `Pipeline.run` and its ledger (#3307) are gone.

## Precedents

- Spark Structured Streaming makes results available per micro-batch, on committed offsets: `markMicroBatchStart` writes the offset log, the sink gets the batch, and `markMicroBatchEnd` writes the commit log ([MicroBatchExecution.scala](https://github.com/apache/spark/blob/81654b27d264533dfd3d9843e26f8a8d9b2b7a2b/sql/core/src/main/scala/org/apache/spark/sql/execution/streaming/runtime/MicroBatchExecution.scala#L1448-L1460), [L1578-L1654](https://github.com/apache/spark/blob/81654b27d264533dfd3d9843e26f8a8d9b2b7a2b/sql/core/src/main/scala/org/apache/spark/sql/execution/streaming/runtime/MicroBatchExecution.scala#L1578-L1654)). Its default trigger is `ProcessingTime(0)` ([DataStreamWriter.scala](https://github.com/apache/spark/blob/81654b27d264533dfd3d9843e26f8a8d9b2b7a2b/sql/core/src/main/scala/org/apache/spark/sql/classic/DataStreamWriter.scala#L464)): the next batch starts when the last one ended, with no wait ([TriggerExecutor.scala](https://github.com/apache/spark/blob/81654b27d264533dfd3d9843e26f8a8d9b2b7a2b/sql/core/src/main/scala/org/apache/spark/sql/execution/streaming/runtime/TriggerExecutor.scala#L79-L99)). `DerivedRefreshes` does the same, and data that arrives during a batch goes into the next one. `AvailableNow` runs batches until all data that was there at the start is read, then stops ([Trigger.java](https://github.com/apache/spark/blob/81654b27d264533dfd3d9843e26f8a8d9b2b7a2b/sql/api/src/main/java/org/apache/spark/sql/streaming/Trigger.java#L107-L124)), as a run does.
- Flink commits a sink's data when a checkpoint completes, in `notifyCheckpointComplete`, so readers see data at each checkpoint, not at the end of a job ([CommitterOperator.java](https://github.com/apache/flink/blob/cd4c2ab77b7109a64605dba18758f682a181bd2e/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/sink/CommitterOperator.java#L157-L180)).
- Materialize keeps a materialized view fresh by "incrementally updating" it "as new data arrives" ([create-materialized-view.md](https://github.com/MaterializeInc/materialize/blob/07eda4c6e03cd9b1f6233c1a3383da3f1f398308/doc/user/content/sql/create-materialized-view.md#L3-L14)).
- Airbyte commits per checkpoint: a state is emitted only when all records before it are written ([GlobalAsyncStateManager.kt](https://github.com/airbytehq/airbyte/blob/10ee3b46fa8c90280d788f37bbace26b262ec805/airbyte-cdk/java/airbyte-cdk/core/src/main/kotlin/io/airbyte/cdk/integrations/destination/async/state/GlobalAsyncStateManager.kt#L30-L38)). But the transform runs after the whole sync: Dagster materializes the Airbyte assets, and so starts dbt, only after `sync_and_poll` returns ([resources.py](https://github.com/dagster-io/dagster/blob/ef5c227a91576661f7c4b8619b855cd95e68ccd5/python_modules/libraries/dagster-airbyte/dagster_airbyte/resources.py#L650-L691)). elt refreshed in that way before this change. elt diverges, because its pipeline is the orchestrator (ADR 0001), and it sees each commit.

## Considered Options

- **Refresh after each pass.** A long first pass gives no derived data until it ends.
- **Refresh on an interval during a pass,** as a `ProcessingTime` trigger with an interval. A time is one more setting, and a refresh that ends early waits with data ready.
- **Ask for a refresh at each commit, one at a time, coalesced.** This option was selected.

## Consequences

- A reader sees derived data during a long pass. It can see the rows of a commit before their derived data; the next refresh gives that data.
- Derived data now describes a pass that is not complete. A reader that concludes from an absence, such as "no page of this program was found", must know that the input is complete. That is the reader's question of completeness, as an event-time watermark answers it in a stream processor.
- Each refresh says its trigger, `RefreshTrigger`: `commit` for a refresh while a pass reads, `pass` for the refresh after the passes. A commit refresh makes new and changed inputs only. A failed input is tried once for each pass, as before this change, so a model that refuses is not asked at each commit (ADR 0007 of `elt-sqlite`). Coalesced requests keep the strongest trigger, `pass`.
- The tests `during a long run, a computed dataset holds the outputs of the rows the first checkpoint committed before the pass ends` `under a watch, a consumer reads the outputs of the rows the first checkpoint committed before the watch yields the pass` and `a run that its signal stops after its pass, while a refresh reads, resolves as its pass did and keeps what it committed` of `elt-sqlite` prove this rule.
