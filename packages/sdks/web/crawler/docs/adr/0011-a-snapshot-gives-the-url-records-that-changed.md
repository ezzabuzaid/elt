# A snapshot gives the URL records that changed

Status: Accepted 2026-11-26 (backlog #4468).

Decision-makers: the context-compiler session context-compiler-e7, which chose the design from the sources of Crawlee, StormCrawler and Nutch (the "STEP 3 DESIGN" note of #4468, 2026-11-25); the elt session that built it (step 3 of #4468). Ezz approved the build ("Build them too", 2026-11-26).

Before this decision, `crawl.snapshot()` gave the whole crawl as one memento: the frontier, the reader states and every URL that a crawl visited, across crawls. `@eltjs/source-web-pages` saved that memento in its state after each page, so each save wrote every known URL again. One real checkpoint was measured at about 583 bytes for each known URL (elt ADR 0035). A crawl of City Center's 10,913 sitemap URLs would then save about 6.4 MB after each page, and a crawl of OpenSooq's ~160k listings about 93 MB. elt ADR 0035 gave a checkpoint keyed entries, which a save puts and removes one by one, so a source can save only what changed. The crawler had to give its URLs as keyed records for that, and it must not depend on elt.

Each crawler that was surveyed keeps one record for each URL, not one document for the crawl. Crawlee keeps a request record for each request, with an `orderNo` that gives its place in the queue (crawlee-storage c1f85223, `request_queue.rs`, lines 74-96; crawlee 1c2a458b, `request-queue.ts`, lines 25-33 and 527-533). StormCrawler's SQL status updater writes one row for each URL (stormcrawler 6f64162d, `StatusUpdaterBolt.java`, lines 106-116 and 148-188). Nutch keeps one `CrawlDatum` for each URL (nutch a53a5ef4, `CrawlDatum.java`, lines 63-75).

## Decision

1. **A snapshot gives the memento and the URL records that changed since the last snapshot.** `crawl.snapshot()` gives `{ memento, urls: { put, remove } }`. The memento is small: the reader states and the starting origins of an unfinished crawl, or null once the crawl is complete, and the starting pages. `put` maps each URL whose record changed to its record. `remove` holds each URL that the crawl found and left without a visit, such as a URL that `robots.txt` disallows or that no reader admits. Thus a snapshot drains what changed: two snapshots with no step of the crawl between them give an empty second one.
2. **A URL record is what the last visit got, the URL's place in the frontier, or both.** `CrawlUrl` is `{ known: KnownUrl, pending: PendingUrl | null } | { known: null, pending: PendingUrl }`, so a record that is neither cannot be built. `PendingUrl` is `{ entry, order }`: the frontier entry, and its place in the order found, as Crawlee's `orderNo`. A known URL is never removed: the crawl keeps it forever, as it did before.
3. **The record of a URL changes where the crawl changes it.** It changes when the crawl adds or merges a frontier entry (a new entry takes the next order; one that moves to another priority goes behind its origin's URLs there and takes the next order too), when the next entry is requested after a visit (the visit is committed, and the entry leaves the frontier), when the host fails a page after its turn, and when the crawl drops an entry. A move of an entry into the held set of a blocked origin changes no record.
4. **A crawl resumes from the memento and every record.** `crawl(starts, saved, options)` takes `saved` as `{ memento, urls }`, with `urls` a `ReadonlyMap` from each URL to its record, or null for a crawl that knows no URL. It checks each record with its schema. It sorts the pending records by their order, whatever order the host's store gives them in, and the next URL that the crawl finds takes the order after the largest.
5. **`crawl.complete` tells whether the crawl requested every URL it had.** It replaces `snapshot().crawl === null`, and it changes nothing that the next snapshot gives.
6. **The host applies every snapshot in order.** It removes the URLs of `remove` and puts the records of `put`, with the memento, in one save. `@eltjs/source-web-pages` keeps the memento in its state and the records in the `crawl` space of the checkpoint's keyed entries, which elt scopes to the input's partition (elt ADR 0035). The crawler exports `applySnapshot(saved, snapshot)`, which applies one snapshot to what a host keeps in memory and gives a new value that `crawl()` takes, with `null` for a crawl that knows no URL: immer ships `applyPatches(base, patches)` beside `produceWithPatches`, Yjs ships `applyUpdate(doc, update)` beside the updates that a document emits, and Automerge ships `applyChanges(doc, changes)` beside `getChanges`. It changes no value through JSON: a store does that.
7. **The crawler keeps its own copy of the shape of a change.** `{ put, remove }` is also the shape of a STATE's entries in elt and of `KeyedChanges` in `@zukhruf/snapshot-differential`. The crawler depends on neither, so the two-line type stays a copy in each package.

## Considered Options

- **Keep the whole memento in each snapshot.** Each save writes every known URL again: about 93 MB after each page at OpenSooq's size. This option was rejected.
- **A store owned by the crawler.** A second transaction could make a URL's visit durable before its page's records, and the crawler would depend on a store (elt ADR 0035). This option was rejected.
- **Give only the known URLs as records, and keep the frontier in the memento.** The frontier holds thousands of URLs on a large site, so each save would still write all of them. This option was rejected.
- **Order the frontier by URL on resume.** A store that reads by key gives the URLs in the order of their keys, so a resumed crawl would request an origin's URLs in another order than it found them. This option was rejected.
- **One record for each URL, known or pending or both, with an order.** This option was selected.

## Consequences

- A save writes what changed since the last save: the page handed out before, now visited, and what this page found. Step 5 of #4468 measures the bytes of a checkpoint on a real crawl.
- A host must save every snapshot. A snapshot that the host drops loses its changes, so the host cannot save only some snapshots.
- A host that kept the memento as one value must now keep the records too. `@eltjs/source-web-pages` does.
- An old memento is not read: its frontier and its known URLs are not records, so a crawl from it starts with no known URL. No migration exists.
- The record of a pending URL that the crawl merges again with the same roles is written again. Telling such a merge from a change would cost a comparison for each finding.

## Confirmation

- `src/snapshot.test.ts` of this package: a crawl stopped after each of its 7 entries and resumed from every snapshot that `applySnapshot` applied, each record and memento through JSON as a store keeps them, hands out the rest and ends with the pages, `nextDue()` and `failures()` of a crawl that was not stopped; a snapshot puts only the page handed out before and what this page found; a second snapshot is empty; `complete` is false while the crawl runs, when a block holds URLs back and after `abandon()`, is true at the end, and keeps the changes; a disallowed URL and a URL that no reader admits leave the records; a page that the host fails in its own turn or in a later turn is a failure of the resumed crawl; a crawl resumed from records in the order of their keys requests the URLs in the order found, also those found after an earlier resume; a record that is neither known nor pending is refused.
- `src/link-discovery.test.ts` of `@eltjs/source-web-pages`: a read through a real `Pipeline` and `SQLiteCheckpointStore`, stopped after two pages, resumes from the records of the `crawl` space: the page visited before the stop is not requested again, the page that only the home page links is still loaded, and the store keeps no record of the disallowed URL. `src/web-source.test.ts`: a crawl that a block leaves unfinished does not end its scan.
- Mutation results, each mutant in memory: every claim was caught. A snapshot that puts every known URL, one that does not drain, a `complete` that drains or is always true, a disallowed or unadmitted drop that is not marked, a resume that does not sort by order or restarts the order at 0, a record that is not checked, a visit that is not marked at its commit, an off-turn `fail()` that is not marked, a web source that does not save or read the `crawl` space or drops its removes, and a web source that ends the scan of an unfinished crawl or reports it complete each failed its test. In the first round the commit's mark and a second mark of the entry handed out before survived, since each stood in for the other; the second mark was removed, and the commit's mark was then caught.
