# Code copied from elt-postgresql

The SQL Server destination is the third destination that numbers its commits and keeps table targets. The Rule of Three counts places, not packages: knowledge that a third place needs moves into `@eltjs/elt`, and all three destinations use it (ADR 0012). Code that only the SQL dialect makes alike is not one knowledge, and it stays in each destination. Knowledge that only elt-postgresql and this package hold is copied, at strike 2, and a fix in one copy is made in the other copy too, and the commit names both files.

Paths on the left are in `packages/destinations/postgresql/src`. Paths on the right are in `packages/destinations/sqlserver/src`.

## Copied with changes

| elt-postgresql                                                                                          | elt-sqlserver                                                                                     | What differs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `postgres-history.ts`, `rowHash`                                                                        | `sql-server-history.ts`, `rowHash`                                                                | None in the hash of the values that the stage carries. No file is stored yet, so no value is the bytes of a file. elt-sqlite hashes the values that SQLite stores, which change for another reason, so it is not a third copy.                                                                                                                                                                                                                                                                                                                                             |
| `postgres-writer.ts`, the batches of `prepare` (1,000 rows or 16 MiB of JSON)                           | `sql-server-writer.ts`, the batches of `prepare`                                                  | One `nvarchar(max)` parameter that `OPENJSON … WITH` reads (ADR 0011), not `json_array_elements`. A row is a JSON array of its place, its operation, its values and its hashes, each hash as hex. elt-sqlite writes each row in its own process, with no batch.                                                                                                                                                                                                                                                                                                            |
| `postgres-writer.ts`, `PostgresWriter`, and `postgres-append-writer.ts`                                 | `sql-server-writer.ts`, `SqlServerWriter`, and `sql-server-append-writer.ts`                      | The same split: the base class claims the target, stages each operation with `_elt_op` and clears; each mode gives its `merge`. The key hash is of `keys`: the declared key of an append, the copy's key of a deduplicating load. Its index is named after the table and the key, and `storedFit` refuses a table without it, since its stored hashes are of another key. A `merge` gives whether it changed a row, so a commit that changed none takes back its commit row.                                                                                               |
| `postgres-deduplicating-writer.ts`, `#accepted`, `merge`, `inspect`, `encode`, `deletionRow`            | `sql-server-deduplicating-writer.ts`, `#reduced`, `merge`, the same names                         | One `MERGE` on `_elt_key_hash` from the reduced stage (ADR 0005), not a `DELETE` and an `INSERT … ON CONFLICT`. The reduced stage keeps the last deletion of a key when no record follows it, and marks a record that follows a deletion (`_elt_last`), which replaces the row with no guard, as the `DELETE` and `INSERT` of Postgres do. A text cursor compares as `varchar(max)` in `Latin1_General_100_BIN2_UTF8`, for `COLLATE "C"`. `inspect` reads `TOP (1)`, not `LIMIT 1`. The unique index is made with the table (`sql-server-writer.ts`), not by `initialize`. |
| `postgres-history.ts`, `TargetHistory.keep`                                                             | `sql-server-history.ts`, `TargetHistory.keep`                                                     | It takes the statement that changes the target, with `OUTPUT deleted.*`, and runs it inside its `INSERT … SELECT` (composable DML), not a `SELECT` of the rows before the change. It keeps the output rows whose `committed_in` is not null, so the null row of an insert stays out; ADR 0005 filters by `$action` to the same effect. It does not follow the shape of the target yet (S2c).                                                                                                                                                                               |
| `postgres-writer.ts`, `replaces`, `kept`, `#unmatched` and `#replace`                                   | `sql-server-writer.ts`, the same names                                                            | A row is told apart by `_elt_row` (ADR 0003), not `ctid`. The rows that leave go in one `DELETE … OUTPUT deleted.*` through `TargetHistory.remove`. `#replace` gives whether it changed a row, so a pass that brings the same rows again takes back its commit row and gives no position. The first commit is a state of the `Claim` of `prepare`, not a flag. No index waits for the rows that leave: the key-hash index is made with the table, and what stays matches records, one for each key.                                                                        |
| `postgres-overwrite-writer.ts`, `PostgresOverwriteWriter`                                               | `sql-server-overwrite-writer.ts`, `SqlServerOverwriteWriter`                                      | None.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `postgres-deduplicating-writer.ts`, `replaces` and `kept` of `overwrite_dedup`                          | `sql-server-overwrite-deduplicating-writer.ts` and `kept` of `sql-server-deduplicating-writer.ts` | An `overwrite_dedup` copy is a class of its own, not a test of the mode in the deduplicating writer. `kept` selects the records of the reduced stage (`#reduced`), not of `#accepted`.                                                                                                                                                                                                                                                                                                                                                                                     |
| `postgres-history.ts`, `TargetHistory.remove`                                                           | `sql-server-history.ts`, `TargetHistory.remove`                                                   | One `DELETE … OUTPUT deleted.*` that `keep` runs inside its `INSERT … SELECT`, not a `keep` and then a `DELETE`. It gives how many rows it kept.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `postgres-checkpoint-store.ts`                                                                          | `sql-server-checkpoint-store.ts`                                                                  | One key of `SqlServerStore` of `@zukhruf/mutex/sqlserver` for each copy id (ADR 0009), as elt-sqlite holds one of `SqliteStore`; the recursive `#held` is a copy of `session` of `sqlite-checkpoint-store.ts`. ## Knowledge in all three, written apart

- The external schema: a reader sees the columns of a stream and `loaded_at`. SQL Server keeps it in the columns that `sql-server-writer.ts` gives `TargetReaderView`, as Postgres does, and in the reserved names of `sql-server-identifiers.ts`, which add `_elt_row` and `_elt_key_hash`.
- A load of a connector that is still open when a new load of the connector opens is closed by the new load, and a closed load cannot commit. SQL Server holds a shared lock on the row of the load with `HOLDLOCK`.
- A clear is a load of one commit, which does not close the open loads of its connector (`commitOnce`).
- The DDL of the objects that the targets of one database share takes the lock of its schema in a transaction of its own: an advisory lock in Postgres, an application lock here (`lockSchema`), a write transaction of the file in SQLite.
